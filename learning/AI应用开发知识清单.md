## 环节 1　HTTP / JSON：一切的载体

**① 逼出它的原因**：这是起点。没有它，前后端无法对话。

**② 核心概念**

## 环节 5　流式输出（SSE）：让用户不用干等

**① 逼出它的原因**：大模型生成一段 500 字的回答要 5-10 秒。如果等全部生成完再返回，用户盯着转圈 10 秒会以为卡死了。而**人阅读的速度远快于模型生成的速度**——边生成边显示，感知延迟接近 0。

**② 核心概念**
SSE（Server-Sent Events）是一种"服务器持续往客户端推数据"的协议。数据格式极简：

```
data: {"choices":[{"delta":{"content":"你"}}]}

data: {"choices":[{"delta":{"content":"好"}}]}

data: [DONE]
```

**两个容易搞错的点**：
1. **事件之间用空行（`\n\n`）分隔**，不是单换行
2. 网络传输会**把数据切成任意大小的块**，一个中文汉字 3 个字节可能被切到两个 chunk 里。所以前端必须用 `decoder.decode(value, {stream: true})`（`stream: true` 是关键，它让解码器记住未完成的多字节序列），并且**把最后一段不完整的留在 buffer 里等下一轮**

**③ 你的代码在哪**
- 后端流式生成：[pdf_qa_optimized.py:129-140](pdf_qa_optimized.py#L129-L140)
- 前端解析：[web/app.js:165-185](web/app.js#L165-L185) —— **这段写得很好**，注释和 buffer 处理都对
- 你**升级过一版协议**：早期的 `/ask/stream` 是纯文本流，v7.5 的 `/ask/v2` 是**结构化的 SSE**（[pdf_qa_optimized.py:241-357](pdf_qa_optimized.py#L241-L357)），事件类型有 `meta` / `sources` / `delta` / `done` / `error` 五种

**④ 关键参数与取舍**
- **为什么不用 `EventSource`？** 这是 `web/app.js:6-8` 里你自己写的注释：`EventSource` 只支持 GET，而提问需要 POST 传 JSON。所以只能用 `fetch` 读流，然后**手动按 `\n\n` 拆分事件**。这个取舍能讲出来，说明你真的思考过
- **`/ask/v2` 的耗时埋点**（[pdf_qa_optimized.py:296-297](pdf_qa_optimized.py#L296-L297) + [web/app.js:284-289](web/app.js#L284-L289)）：把向量检索、重排序、模型生成三段耗时分别推给前端显示。**应届生项目里极少有人做这个**，这是很强的加分项

**⑤ 面试怎么答**
> 我用 SSE 做流式。后端用 FastAPI 的 `StreamingResponse` 包一个生成器，每个 token 到了就 yield；前端用 fetch 读 response.body 的 reader，按空行拆事件。这里有个坑：网络会把数据切成任意块，中文可能被从中间切断，所以解码要用 `{stream: true}`，并且 buffer 里最后一段不完整的要留到下一轮。

## 环节 6　关键词检索（BM25）：最古老也最顽强的方案

**① 逼出它的原因**：模型的知识是训练时冻结的，不知道你的私有文档（员工手册、产品说明）。要么把整本书塞进 prompt（超长且贵），要么**先检索出最相关的几段**再塞。这就逼出了"检索"这一环。

**② 核心概念**
BM25 是关键词检索的经典算法。核心思想：

> 一个词在**这篇文档里出现得越多**（词频 TF），在**所有文档里出现得越少**（逆文档频率 IDF），这个词就越能代表这篇文档。

公式里有 **k1** 和 **b** 两个参数：
- `k1` 控制"词频的饱和速度"——一个词出现 100 次和 200 次，重要性不该差一倍，所以要饱和
- `b` 控制"文档长度归一化"——长文档天然词多，要打折，`b=0` 不打折，`b=1` 完全归一化

**③ 你的代码在哪**
[eval/retrievers.py:63-140](eval/retrievers.py#L63-L140)，`k1=1.5, b=0.75`（[retrievers.py:87](eval/retrievers.py#L87)），用 jieba 分词（[retrievers.py:96-99](eval/retrievers.py#L96-L99)）

**④ 关键参数与取舍**
- `k1=1.5, b=0.75` 是 BM25 的经典默认值，直接用没问题
- **中文必须分词**。英文天然有空格，中文"年假规定"是一整个字符串，不切词的话"年假"和"规定"永远匹配不上。jieba 就是干这个的
- **你自己搭了倒排索引**（[retrievers.py:107-114](eval/retrievers.py#L107-L114)）：`postings[词] = [(文档号, 词频), ...]`。这样打分时只遍历命中的文档，而不是扫全部 934 篇。这是 BM25 能跑到 **7.1ms** 的原因

**⑤ 面试怎么答**
> BM25 是基于词频和逆文档频率的关键词检索。中文要先 jieba 分词。我实现了倒排索引——建立"词 → 出现该词的文档列表"的映射，检索时只遍历命中词的文档，而不是全量扫描。

## 环节 7　向量检索与 Embedding：语义相似度

**① 逼出它的原因**：关键词检索有个致命缺陷——**它不认识同义词**。你的 README 里自己写了这个动机（`README.md:48`）："搜『休假』找不到『年假』，搜『请假』找不到『调休』"。因为 BM25 只看字面，"休假"和"年假"是两个毫不相关的字符串。

**② 核心概念**
Embedding 模型把一段文本压缩成一个**固定长度的数字向量**（bge-small-zh-v1.5 输出 512 维）。关键在于：**语义相近的文本，向量也相近**。

"年假有多少天"和"annual leave policy"的向量会非常接近，尽管没有一个字相同。

相似度用**余弦相似度**衡量——两个向量的夹角余弦，1 表示方向完全一致，0 表示正交无关：

```
cos(A, B) = (A · B) / (|A| × |B|)
```

**③ 你的代码在哪**
- 加载模型：[pdf_qa_optimized.py:21](pdf_qa_optimized.py#L21) `SentenceTransformer("BAAI/bge-small-zh-v1.5")`
- 手写余弦相似度：[pdf_qa_optimized.py:122](pdf_qa_optimized.py#L122)

**④ 关键参数与取舍**
- **归一化技巧**：如果先把向量归一化成单位长度（`normalize_embeddings=True`，[retrievers.py:178](eval/retrievers.py#L178)），那么余弦相似度就等于**点积**，省掉两次开方和除法。你的 `retrievers.py` 做了归一化，但 `pdf_qa_optimized.py:122` 每次都在算范数——**这是个可以优化的点**（934 篇文档 × 每次两个 `np.linalg.norm`）
- **512 维的取舍**：维度越高表达能力越强但越慢越占内存。bge-small 是 512 维（small 版），bge-large 是 1024 维。选 small 是为了 CPU 能跑
- **bge 的查询指令前缀**：bge 系列模型设计上要求**查询侧**加一句 `"为这个句子生成表示以用于检索相关文章："`，文档侧不加。你在 [retrievers.py:43](eval/retrievers.py#L43) 定义了这个常量，但**从未启用**（`use_instruction` 全仓库没有一处设为 True）。注释里写了原因：为了复现原系统的真实行为。**这个决定是对的**——只有不加前缀才能公平对比，但你要知道这个选项存在

**⑤ 面试怎么答**
> 用 sentence-transformers 加载 bge-small-zh-v1.5，把文本编码成 512 维向量，用余弦相似度算相关性。如果向量归一化了，余弦相似度就退化成点积，可以省掉算范数。
>
> 追问「bge 有什么使用注意事项」→ bge 设计上要求查询侧加指令前缀，文档侧不加，否则效果会掉。我评测时没加，是为了和原系统做公平对比。

## 环节 8　分块（Chunking）：RAG 质量的第一道关

**① 逼出它的原因**：两个硬约束。
1. **模型有长度上限**：bge 的 `max_position_embeddings` 是 512 token（[eval/cache/finetuned_model/config.json](eval/cache/finetuned_model/config.json)）。整篇文档塞不进去
2. **检索粒度要匹配问题粒度**：用户问"年假几天"，需要的是一小段，不是整本手册

**② 核心概念**
把长文档切成若干小块，每块单独编码、单独检索。

**你做了三代分块**，这个演进过程本身就是最好的教材：

| 代 | 函数 | 策略 | 缺陷 |
|---|---|---|---|
| 一代 | `chunk_text`（[pdf_qa.py:28-58](pdf_qa.py#L28-L58)） | 按标点切，**有"切不动就按字数硬切"的兜底** | 语义不完整 |
| 二代 | `smart_chunk`（[pdf_qa_optimized.py:59-71](pdf_qa_optimized.py#L59-L71)） | 按"第X章/第X条"结构切 + **相邻块重叠 50 字** | **丢掉了长度上限**（见下） |
| 三代 | `smart_chunk_v2`（[eval/chunking.py:120-156](eval/chunking.py#L120-L156)） | 结构切 + **按句装箱到 400 token** + 50 token 重叠 | 单句超长时仍有漏洞 |

**③ 关键概念：为什么要重叠（overlap）**

假设文档里有一句关键的话正好跨越切分边界：

```
...年假为 5 天。入职满 3 年的员工，年
假增加至 10 天。病假期间工资...
         ↑ 切分点在这里
```

切成两块后，前半块结尾是"年"，后半块开头是"假增加至 10 天"。**两块的语义都不完整，检索时可能都匹配不上。**

解决办法：切完以后，**给每一块的开头拼上前一块的末尾 50 个字符**（[pdf_qa_optimized.py:68](pdf_qa_optimized.py#L68)）：

```python
if i > 0: c = chunks[i-1][-overlap:] + "\n" + c
```

这样跨边界的信息在两块里都完整存在。

  max_len=512 -> 评测语料截断 63.5%

**63.5% 的文档超过 bge 的 512 上限被截断**，而 BM25 是基于完整文档算词频的——**这就是向量检索打不过 BM25 的头号嫌疑**。这个发现直接引出了你的方案 E/F。

**⑤ 面试怎么答**

> 追问「你怎么知道块大小合适」→ 我用真实 tokenizer 量了语料长度分布，发现均值 582 token，512 上限会截断 63.5%，所以后来改成按句装箱到 400 token，留出余量。

## 环节 9　重排序（Rerank）：粗排 → 精排

**① 逼出它的原因**：向量检索是**双塔（Bi-encoder）**结构——问题和文档**分别**编码成向量，然后算相似度。好处是快（文档向量可以离线预计算），坏处是**问题和文档从来没有"见过面"**，交互信息丢失了。

**② 核心概念：Bi-encoder vs Cross-encoder**

| | Bi-encoder（向量检索） | Cross-encoder（重排序） |
|---|---|---|
| 输入 | 问题、文档**分别**过模型 | 问题+文档**拼在一起**过模型 |
| 输出 | 两个向量，算相似度 | 一个相关度分数 |
| 速度 | 快（文档向量可预计算） | **慢**（每对都要现算，无法预计算） |
| 精度 | 较低 | **高**（能建模词级交互） |
| 用途 | **粗排**——从 1000 篇里捞出 50 篇 | **精排**——把 50 篇精确排到前 3 |

**核心工程思想：用快的做粗筛，用准的做精选。** 这就是"两阶段检索"。

**③ 你的代码在哪**
[pdf_qa_optimized.py:123-126](pdf_qa_optimized.py#L123-L126)：

```python
top10 = np.argsort(scores)[-10:][::-1]              # 粗排：向量召回 Top-10
pairs = [(req.question, doc_chunks[i]) for i in top10]
re_scores = reranker.predict(pairs)                 # 精排：CrossEncoder 打分
results = [...][-3:][::-1]                          # 取 Top-3
```

**④ 你的实测数据（非常重要，可能推翻你简历上的说法）**

重排序在你的评测里是 **P@1 最高**的方案，但代价惊人：

| 方案 | P@1 | 耗时 |
|---|---|---|
| A BM25 | 0.9164 | **7.1 ms** |
| C 向量+重排序 | **0.9243** | **6345.7 ms** |
| F 分块+微调 | 0.9208 | **18.3 ms** |

- 重排序只把 P@1 从 0.9164 提到 0.9243（**+0.79pt**），代价是**慢 890 倍**
- 而方案 F 只低 0.35pt，**快 347 倍**
- 更关键：**C 的 Recall@10 与 B 完全相同（都是 0.9460）**。因为召回候选数（10）和返回条数（10）一样，**重排序只能改排序，不能提升召回上限**

**这个结论比"我加了重排序所以更好"有价值得多。** 它说明你有工程判断力——知道什么时候**不该**用最强的方案。

**⑤ 面试怎么答**
> 我用两阶段检索：先用向量做粗排召回 Top-10，再用 CrossEncoder（bge-reranker-base）对每一对做精排，取 Top-3。CrossEncoder 把问题和文档拼在一起过模型，能建模词级交互，比双塔准，但每对都要现算，没法预计算文档向量，所以只能用在精排阶段。
>
> 追问「效果怎么样」→ 我做了评测，重排序把 P@1 从 0.859 提到 0.924，是单方案里最高的；但耗时 6345ms，是 BM25 的 890 倍。而我另一条路线「分块+微调」能到 0.921，只要 18ms。所以如果重来，我会优先选后者，重排序只在延迟不敏感的离线场景用。

## 环节 10　Agent 与 Function Calling：让模型会用工具

**① 逼出它的原因**：模型只有训练时的知识，不会查天气、不会算数、不知道你的私有数据。要么你把所有东西塞进 prompt，要么——**让模型自己决定什么时候调用什么工具**。

**② 核心概念**
Function Calling 的完整回路：

```
1. 你告诉模型：我有这几个工具（JSON Schema 描述名字、参数、类型）
2. 模型判断：这个问题需要调 get_weather，参数是 {"city": "银川"}
3. 模型返回 tool_calls（它不执行，只是说"我要调这个"）
4. 你的代码真正执行函数，把结果作为 role="tool" 的消息回填
5. 再调一次模型，它拿着结果生成最终回答
```

**关键认知：模型不执行任何代码，它只是输出"我想调用 X"的结构化意图。执行永远是你的代码在做。**

**③ 你的代码在哪**
- 工具定义与回路：[rag_agent.py:149-192](rag_agent.py#L149-L192)，**最多循环 5 轮防死循环**
- 原理 demo：[agent_demo.py:138-142](agent_demo.py#L138-L142) 演示 `role:"tool"` 消息怎么回填
- MCP：[mcp_demo.py:67-100](mcp_demo.py#L67-L100) 用装饰器自动注册工具 + `inspect.signature` 推断参数 schema，对比"手写 tools 数组"

**④ 关键参数与取舍**
- **为什么要限轮次？** 模型可能陷入"调工具 → 结果不满足 → 再调"的循环，无限烧 token。5 轮是兜底
- **⚠️ 安全问题**：[mcp_demo.py:19](mcp_demo.py#L19) 和 [:119](mcp_demo.py#L119) 用了**完全裸的 `eval(expr)`**。目前只是 demo 没接模型所以没事，但**一旦照这个模式把 eval 接上 Function Calling（参数由模型生成），就是远程代码执行漏洞**。相比之下 `rag_agent.py:64-71` 有白名单过滤。**这个不一致必须在面试前想清楚怎么解释**

**⑤ 面试怎么答**

> 追问「eval 安全吗」→ 我的 demo 里有一处直接 eval 表达式来当计算器。这个在生产绝对不能这么写，因为表达式可能来自模型，必须做白名单过滤或者用安全的表达式解析库。我在另一个文件里做了字符白名单，但严格说也不够——比如允许 `**` 就能构造出计算量爆炸的表达式。

**主动暴露安全问题，说明你有安全意识。** 掩盖它才是危险的。

## 环节 11　多智能体协作：用角色分工换质量

**① 逼出它的原因**：这是你**自己发现的**问题。你简历上写得很清楚：

> 一问一答式调用大模型，产出经常是套话。

一次调用只有一个视角，没有自我纠正的机会。

**② 核心概念：4 个角色 + 一条接力棒**

```
策划师 → 执行者 → 审查员 → 优化者 → （回到执行者）
   │                 │
   │                 └── 打分 < 8 且轮次 < 3 → 继续
   └── 方案只传一次      打分 >= 8 且轮次 >= 2 → 结束
```

关键在于 **`current_work` 这个"接力棒"**——上一轮的产物作为下一轮的输入往下传（[agent_studio_api.py:109-121](agent_studio_api.py#L109-L121)）。

**③ 三个设计决策（面试核心）**

**(a) 为什么用"对比式评估"而不是"绝对打分"？**
模型的绝对打分极不稳定（同样的东西今天给 7 分明天给 5 分）。但如果告诉它"这是上一版，这一版改进了什么"，它有了**参照系**，评估就稳定得多。代码在 [agent_studio_api.py:126-129](agent_studio_api.py#L126-L129)：只有 `round_num > 0` 才把 `prev_work` 传给审查员。

**(b) 为什么阈值是"≥8 且 ≥2 轮"？**
[agent_studio_api.py:149](agent_studio_api.py#L149)：`if final_score >= 8 and round_num >= 1`
- 只判分数不判轮次 → 第一轮就 9 分直接结束，没有任何迭代
- **模型有自我偏好（self-preference）**，第一轮分数普遍虚高，不可信
- 强制至少 2 轮，逼出一次真正的"审查-修改"循环

**(c) 解析失败为什么默认给 7 分？**
[agent_studio_api.py:138-141](agent_studio_api.py#L138-L141)：正则匹配不到分数时 `final_score = 7`。
**7 分低于阈值 8，所以会继续迭代。** 这是 **fail-safe（失效安全）设计**——解析失败时宁可多迭代一轮，也不要误判为"已完成"而提前结束。这个细节面试官会眼前一亮。

**④ 你的实测数据（两条真实的分数曲线）**

```
任务3：审查员 5/10 → 2/10 → 7/10   （三轮跑满，从未到 8）
任务4：审查员 7/10 → 7/10 → 7/10   （三轮跑满，卡住不动）
```

**这两条曲线暴露了系统的真实局限，是绝佳的"踩坑故事"：**

- **5→2→7 非单调** → 单次打分噪声极大，**绝不能信第一轮的分数**，这直接印证了"强制 2 轮"的设计
- **任务4 卡在 7 分三轮不动** → 要么阈值 8 定得太高（模型很少给 8+），要么对比式评估让分数"锚"住了（"跟上一版差不多，还是 7 分"）。结果是**明明在改进但分数不涨，白白多跑两轮烧 token**

**⑤ 面试怎么答**
> 我用 4 个角色构成协作循环：策划、执行、审查、优化，上一轮的产出作为下一轮的输入往下传，最多 3 轮。
>
> 一开始审查员只会说好话、打分虚高，迭代等于空转。我改了两点：一是**对比式评估**——每轮必须先写清"相比上一版改了什么"，给它一个参照系；二是**硬性要求**至少列 3 条具体问题，并规定输出格式 `## 评分：X/10`，因为我的代码要用正则解析这个分数来决定是否继续。
>
> 终止条件是分数 ≥8 且至少迭代 2 轮。强制 2 轮是因为**模型有自我偏好，第一轮分数普遍虚高不可信**。另外正则解析不到分数时我默认给 7 分，低于阈值所以会继续迭代——这是 fail-safe，宁可多跑一轮也不要误判完成。
>
> 追问「效果呢」→ 我回看了历史任务的分数曲线，发现问题：有三轮都停在 7 分一次没到阈值的，说明**阈值定得太高或者对比式评估让分数锚住了**，导致明明在改进但分数不涨，白白多烧两轮 token。这是我下一步要优化的地方。

## 环节 12　数据层：MySQL 存什么，Redis 缓存什么

**① 逼出它的原因**：服务重启，聊天记录全丢（`README.md:107`）；相同问题反复调 API，费钱又慢（`README.md:109`）。

**② 核心概念**

| | MySQL | Redis |
|---|---|---|
| 数据在哪 | 磁盘 | 内存 |
| 速度 | 毫秒级 | 微秒级 |
| 持久化 | 天然 | 可选（RDB/AOF） |
| 适用 | **必须存住的数据**：任务、消息、用户 | **可重建的热数据**：缓存、锁、会话 |

**判断标准很简单：这份数据丢了会不会有严重后果？**
- 聊天记录丢了 → 用户生气 → **MySQL**
- 缓存丢了 → 下次查库重建 → **Redis**

**③ 你的代码在哪**

**MySQL**（[agent_studio_api.py:27-36](agent_studio_api.py#L27-L36)）：
```sql
studio_tasks  (id, title, task_type, requirement, status, created_at)
studio_steps  (id, task_id FK→studio_tasks, agent, action, content, score, created_at)
```
**外键 `ON DELETE CASCADE`**：删任务时自动删掉它的所有步骤，不用手动清理。这是设计得好的地方。

**Redis 的两个用法**（[agent_studio_api.py:27-56](agent_studio_api.py#L27-L56)）：

1. **分布式锁防重复提交**（[acquire_lock:27](agent_studio_api.py#L27)）
   - 痛点：一次协作跑几十秒、烧 4-12 次 API 调用，用户手抖点两下就跑两份
   - `SET key 1 NX EX 300` —— 一条命令**原子地**完成"判断不存在 + 写入 + 设过期"
   - **为什么用 Redis 不用 MySQL**：MySQL 要 `SELECT ... FOR UPDATE` + 自己维护过期时间，重得多
   - **为什么带 EX**：进程崩了锁自动释放，不会死锁

2. **Cache-Aside 缓存**（[get_task:262](agent_studio_api.py#L262)）
   - 读：先查 Redis，未命中查 MySQL 再 `setex 300`
   - 写：**删缓存**，不是更新缓存（[save_step:202](agent_studio_api.py#L202)）
   - **为什么删而不是更新**：并发下两个写可能按错误顺序落地导致脏数据；直接删掉，下次读自然重建，简单且安全

**④ 关键设计：降级**
所有 Redis 调用都包了 try/except（[agent_studio_api.py:27-56](agent_studio_api.py#L27-L56)）。**Redis 挂了只损失锁和缓存，主流程照跑。缓存组件不能拖垮主流程**——这句话面试时主动说出来。

**⑤ 面试怎么答**
> 我有两类数据。任务和每一步产出必须存住，用 MySQL，steps 表用外键关联 tasks 并设了 ON DELETE CASCADE，删任务自动清理步骤。
>
> Redis 用在两个地方：一是分布式锁，用 `SET NX EX` 防止用户重复提交——一次协作要跑几十秒烧十几次 API 调用，重复提交代价很高；二是任务详情的 Cache-Aside 缓存，因为 steps.content 每条都是几千字的模型输出，读多写少。写路径我用的是**删缓存**而不是更新缓存，避免并发写导致的脏数据。
>
> 所有 Redis 调用我都做了降级，Redis 挂了就放行/查库，不能因为缓存组件把主流程拖垮。

## 2.1　为什么向量检索会输给 BM25？

**反直觉的事实**：你花大力气搭的语义检索，P@1 只有 **0.8590**，输给最古老的 BM25 的 **0.9164**。

**这不是你的实现错了，是通用向量模型的固有局限。** 两个原因：

**原因一：领域不匹配**
bge-small-zh-v1.5 是在通用语料上训练的。你的评测语料是 CMRC2018 的文言文/历史文本（从 `_leakcheck` 里那些"讨伐孙秀之功获加授散骑常侍"能看出来）。通用模型对这种文本的表示能力不足。

**验证**：微调 → **0.8590 → 0.8895，+3.05pt** ✅ 假设成立

**原因二：长文档被截断**
bge 上限 512 token，而语料**均值 582 token，63.5% 被截断**。BM25 却是基于完整文档算词频的——**它在信息上占了大便宜**。

**验证**：分块 → **0.8590 → 0.9017，+4.27pt** ✅ 假设成立

**合体**：分块+微调 → **0.9208，+6.18pt**，且两个增益可叠加 → **说明两条假设各自独立成立**

**这就是完整的科学闭环。** 面试时这样讲：

> 我原本以为向量检索一定比关键词好，做了评测才发现通用向量模型 P@1 只有 0.859，输给 BM25 的 0.916。我没有直接接受这个结论，而是提了两个假设：一是领域不匹配，二是长文档截断——因为我量了 token 分布，发现 63.5% 的文档超过模型 512 的上限被截断，而 BM25 是基于完整文档做词频统计的。
> 我分别验证：微调提升 3.05 个点，分块提升 4.27 个点，两个合起来提升 6.18 个点，增益可以叠加，说明两个原因都成立且互相独立。

## 2.2　什么是"批内负样本"损失（MultipleNegativesRankingLoss）？

你微调用的是这个损失（[eval/finetune_embedding.py:202](eval/finetune_embedding.py#L202)）。它的巧妙之处值得讲清楚。

**问题**：训练 embedding 需要"正样本对"（问题, 正确文档）和"负样本对"（问题, 错误文档）。但人工标注负样本极其昂贵。

**巧妙的解法**：一个 batch 有 16 个 (问题, 正文档) 对。那么对**第 1 个问题**来说：
- 它自己的那篇文档 = 正样本
- **同 batch 里另外 15 篇文档 = 天然的负样本**

一次前向传播得到 16 个正样本对和 16×15 个负样本对，**零额外标注成本**。

**一个重要的直觉**：随机猜的 loss ≈ ln(batch_size) = ln(16) = **2.77**。你的验证 loss 是 **1.33**，说明模型在未见过的文档上确实显著优于随机。训练 loss 从 0.085 降到 0.022（降 75%），**没有震荡没有 NaN**。

**⚠️ 但也暴露了问题**：验证 loss 几乎不动（1.3401 → 1.3345 → 1.3359），第 3 个 epoch 反而上升。**泛化信号很弱**。原因是验证集是"按文档切分"的（[finetune_embedding.py:62-68](eval/finetune_embedding.py#L62-L68)）——训练时见过的文档不出现在验证集里，这是**更严格但也更真实**的验证设定。**这个设计是对的，不是 bug**。

## 2.3　nDCG 为什么会退化成 `1/log₂(rank+1)`？

你的评测指标里有 Recall@k、MRR@k、nDCG@k（[eval/metrics.py](eval/metrics.py)）。但有个关键前提：

**每条查询恰好只有 1 篇相关文档**（`_datacheck.txt` 确认 qrels 全部 `score=1`，1149 条 query 对应 1149 篇文档，一一对应）。

在这个前提下：
- **Recall@k ≡ Hit Rate@k** —— 因为最多只能召回 1 篇，要么 0 要么 1
- **nDCG 退化** —— nDCG 的定义是 `DCG / IDCG`，只有一篇相关文档时 DCG = `1/log₂(rank+1)`，而 IDCG = `1/log₂(1+1)` = 1，所以 nDCG = `1/log₂(rank+1)`

**你在 [metrics.py:10-19](eval/metrics.py#L10-L19) 的 docstring 里自己点破了这一点。** 这是很诚实、很专业的做法——**知道自己的指标在什么前提下会退化，比会用指标更重要**。

面试可以这样说：
> 我的评测集每条查询只有一篇标准答案，所以 Recall@k 在这个设定下等价于 Hit Rate，nDCG 也退化成了 `1/log₂(rank+1)`。我在代码注释里标注了这个前提，避免误导。

## 2.4　数据泄漏（Data Leakage）：为什么它会让你的指标全是假的？

**这是你做的最专业的一件事，而且你自己可能没意识到它有多重要。**

`eval/data/_leakcheck.txt`：
```
[泄漏检验] train ∩ eval_corpus = 204  <-- 必须为 0
```

**评测语料 934 篇里有 204 篇（21.8%）和训练集逐字相同。**

**为什么这是致命的？**
如果不修，你的模型在训练时**已经见过这 204 篇文档的原文**。那么在这部分评测数据上，它的高分不代表"学会了泛化"，只代表"背下来了"。**指标虚高，整个微调实验的结论都不成立。**

**你做了什么**（`_leakfix.txt`）：
```
未去泄漏: 9236 句对, 2393 篇文档
去泄漏后: 8468 句对, 2189 篇文档
剔除句对: 768   剔除文档: 204
校验（必须为0）: eval语料 ∩ 清洗后训练文档 = 0
```

实现方式是在训练前传入 `exclude_contexts` 参数剔除（[dataset.py:127-182](eval/dataset.py#L127-L182)）。

**面试话术**：
> 我在微调前做了数据泄漏检查，发现评测语料里有 204 篇和训练集逐字重复，占 21.8%。如果不剔除，模型是在"背答案"，指标虚高、结论不成立。我剔掉了 768 个句对，把泄漏降到 0 并做了自校验。
>
> **大部分做 RAG 的人根本不知道要查这个。**

## 2.5　"改完引入的第二个问题"：去重与 id_map

这是个很好的工程细节，展示你理解**改动的连锁反应**。

`_datacheck.txt`：`lc_corpus: (1149, 2)  id唯一=1149  text唯一=934`

**1149 行里只有 934 篇唯一文本，215 篇完全重复。** 重复文档会让同一篇内容在检索结果里占多个位置，**虚高召回率**。

**你的修复**：`load_corpus(dedup=True)`（[dataset.py:57-67](eval/dataset.py#L57-L67)）

**但改完立刻引入了新问题**：qrels（标准答案）用的是**原始** doc id，去重后文档 id 变了，**映射不上了**。

**你的二次修复**：建立 `原id → 保留id` 的映射存进 `df.attrs["id_map"]`，qrels 加载时通过它映射回去（[dataset.py:61-67, 85-96](eval/dataset.py#L61-L96)）。

**面试话术**：
> 我发现语料有 215 篇完全重复，会让召回率虚高，所以做了去重。但去重后立刻引入了新问题：标准答案用的还是原始 id，映射不上了。所以我建了一张 id 映射表，去重时记录"原 id → 保留 id"，加载标准答案时通过映射还原。**这类"改一个地方牵出另一个地方"的连锁问题，是我做这个评测最大的收获。**

`results/smoke/retrieval_20260921_132934.json`：8 条查询跑两个方案，**所有指标恰好都等于 0.875 / 1.0**。

## 坑 1　多智能体的"上一版"传错了

**现象**：审查员明明在对比，但它的意见总是"针对当前版本"，看不出和上一版的差异。

**根因**：`prev_work` 的赋值位置错了。

```python
# 错误写法
for round_num in range(max_rounds):
    work = call_llm(...)          # 先产出新版本
    current_work = work           # current_work 被覆盖了！
    prev_work = current_work      # 此时 prev_work == work，上一版没了
```

**修复**（[agent_studio_api.py:111](agent_studio_api.py#L111)）：把 `prev_work = current_work` **提到循环体最开头**，在 `current_work` 被覆盖之前捕获。

```python
for round_num in range(max_rounds):
    prev_work = current_work      # ← 先抓住上一版
    work = call_llm(...)          # 再产出新版本
    current_work = work
```

**学到了什么**：**变量的生命周期**。赋值顺序错了，逻辑就静默失效——程序不报错，只是结果不对。这类 bug 最难发现。

**面试怎么讲**
> 我的审查员需要对比"这一版和上一版"。一开始它总是给不出有效对比，我以为是提示词问题，改了好几轮提示词都没用。后来读代码才发现是**赋值顺序**错了——我在循环里先更新了 `current_work`，然后才去取"上一版"，这时候取到的已经是当前版本，等于拿自己和自己对比。修复是把捕获上一版的那行提到循环体最前面。
> **这个 bug 不报错，只是静默地让功能失效**，是我第一次体会到"程序跑通"和"逻辑正确"是两回事。

## 坑 2　审查员只会说好话，迭代等于空转

**现象**：第一版产出明显有问题，审查员却给 9 分，循环直接结束。

**根因**：模型的**自我偏好（self-preference bias）**——同一个模型生成和评价，天然倾向于给自己好评。而且提示词只说"审查"，没说"要找出问题"。

**修复**（[agent_studio_api.py:71-82](agent_studio_api.py#L71-L82)）：
1. **对比式评估**：必须有"相比上一版改进了什么"——给它参照系
2. **量化要求**："至少 3 条具体问题，要有针对性，**不能是空话**"
3. **强制格式**：`## 评分：X/10`——让下游能解析
4. **强制 2 轮**：`final_score >= 8 and round_num >= 1`——不信第一轮的分数

**面试怎么讲**
> 模型给自己打分有自我偏好，第一轮普遍虚高。我用了三招：一是把评估改成对比式的，让它写"相比上一版改进了什么"，有了参照系分数就稳定多了；二是硬性要求至少列 3 条具体问题并明确禁止空话；三是代码层面强制至少迭代 2 轮，不信任第一轮的分数。

## 坑 3　正则解析不到分数时的默认值，救了一命

**现象**：审查员偶尔不按格式输出，解析分数的正则匹配失败。

**修复**（[agent_studio_api.py:138-141](agent_studio_api.py#L138-L141)）：`final_score = 7`

**为什么是 7 而不是 10 或 0？**

**7 < 阈值 8，所以会继续迭代。** 这是 **fail-safe（失效安全）** 设计——解析失败时宁可多迭代一轮，也不要误判为"已完成"而提前结束。

对比一下：如果默认给 10，解析失败就会**静默地提前结束迭代**，产出质量下降但你不自知。如果默认给 0，会永远迭代到上限，浪费 token。**7 是"多花一点钱，换不掉质量"的选择。**

**面试怎么讲**
> 我的代码要从审查员的自由文本里用正则抠出分数。如果模型不按格式输出，解析会失败。我设的默认值是 7 分——**故意低于 8 分的阈值**，这样解析失败时会继续迭代而不是误判完成。这是 fail-safe 的思路：**不确定的时候，选择"多花一轮成本"而不是"可能漏掉问题"。**

## 坑 6　63.5% 的文档被静默截断

**现象**：想不通为什么微调前向量检索这么差。

**排查过程**：没有靠猜，而是**用真实 tokenizer 量了长度分布**（`_toklen.txt`）：

```
评测语料 doc 均值 582 token，中位 586，p95=879，最大 975
  max_len=512 -> 评测语料截断 63.5%
```

**根因**：bge 的 `max_position_embeddings` 是 512。超过的部分**被模型静默截断**——不报错、不警告，直接丢掉。而 BM25 是基于完整文档算词频的。

**修复**：分块（方案 E/F），把长文档切成 ≤400 token 的块。

**学到了什么**：**"静默截断"是 RAG 最常见的隐形杀手。** 不报错不代表没问题。必须主动量数据分布，而不是相信"应该没事"。

**面试怎么讲**
> 我发现向量检索效果差，没有直接换模型，而是先量了数据——用真实的 tokenizer 统计语料长度分布，发现均值 582 token，而模型上限是 512，**63.5% 的文档被静默截断了**。这个截断不报错也不警告，是最容易忽略的问题。而 BM25 是基于完整文档做词频统计的，所以在这个对比里它占了便宜。定位到这一点之后，分块方案就顺理成章了。

## 坑 7　分块改了，但没改干净

**现象**：做了分块，但日志里还有截断警告：

出现在 `full_eval.log:23`（方案E）和 `chunk_ft_eval.log:10`（方案F）。

## 坑 12　`redis/` 文件夹和模块遮蔽：一段不必要的魔法代码

**现象**：你的代码里有 5 处这样的写法（[pdf_qa_optimized.py:11-15](pdf_qa_optimized.py#L11-L15) 等）：

```python
import sys
script_dir = os.path.dirname(os.path.abspath(__file__))
sys.path.remove(script_dir)
import redis as redis_lib
sys.path.insert(0, script_dir)
```

意图很明显：**担心 `D:\shuqi\redis\` 这个文件夹被 Python 当成 `redis` 包**，所以先把项目目录从搜索路径里摘掉。

**但实测证明它不成立：**

```
$ cd D:\shuqi && python -c "import redis; print(redis.__file__)"
D:\python\Lib\site-packages\redis\__init__.py     ← 正常
```

**原因**：`redis/` 文件夹里**没有 `__init__.py`**。在 Python 3 里，这种目录只是"命名空间包候选"，而**正规包（有 `__init__.py`）优先级更高**。所以 `import redis` 本来就能拿到正确的包。

**而且这段"防御"本身埋了两个雷**：
1. `sys.path.remove()` 在目录不在路径里时会抛 `ValueError`。IDE 用不同方式启动、`uvicorn --app-dir`、pytest 收集等场景都可能触发
2. 它把项目目录摘掉了，所以 `from config import ...` **必须写在重新 insert 之后**——隐式耦合，谁删了那行 insert 所有文件立刻全崩

**真正该做的**：把 `redis/` 改名为 `redis-win/`（顺便：这个 32MB 的 Windows Redis 二进制**被提交进了 git**，`.git` 目录已经 35MB，其中 32MB 是它）。

**面试怎么讲**
> 我的项目目录里有一个 `redis/` 文件夹放 Windows 版 Redis 二进制，我担心它遮蔽 Python 的 redis 包，就在导入前把项目目录从 sys.path 里临时摘掉。
> 后来我实测发现**这个担心其实不成立**——那个目录没有 `__init__.py`，在 Python 3 里正规包优先级更高，`import redis` 本来就能拿到正确的包。而且这个写法本身有害：`sys.path.remove` 在目录不在路径时会抛异常，还造成了对导入顺序的隐式依赖。
> **这件事教会我：看不懂的"魔法修复"要么搞懂它，要么删掉它。** 真正的解决方案是给文件夹改名，不是写防御代码。

## 坑 13　缓存 key 不带文档维度：换了 PDF 却返回旧文档的答案

**现象**：先上传员工手册问"年假几天"，拿到答案；再上传另一份文档问同样的问题，**直接返回上一份文档的缓存答案**。

## 坑 15　`except: task_id = 1`：把数据库故障降级成数据污染

**现象**：MySQL 挂掉时，所有任务步骤都写到 **id=1 号任务**下面，污染了一条真实的历史记录。

**根因**（[agent_studio_api.py:233-234](agent_studio_api.py#L233-L234) 附近）：
```python
try:
    ...INSERT INTO studio_tasks...
    task_id = cursor.lastrowid
except:
    task_id = 1          # ← 数据库挂了就让数据写到 1 号任务上
```

配套的 `save_step`（[agent_studio_api.py:202](agent_studio_api.py#L202)）**只吞异常不报错**，所以整个过程完全静默。

同样的问题在 `interview_api.py:135`（`except: iid = 1`）。

**顺带还有个连接泄漏**：`conn/cursor` 在 try 里创建，异常分支直接跳出，`conn.close()` 永不执行。

**正确处理**：**宁可让接口返回 500，也不要把数据写到错误的地方。** 数据污染比报错严重得多。

**面试怎么讲**
> 我一开始为了避免接口报错，给数据库操作都加了兜底，插入失败就退化成 `task_id=1`。后来意识到这是**用数据污染换表面上的"不报错"**——MySQL 挂了的时候，所有新任务都会写到 1 号任务下面，把一条真实记录搞脏，而且因为我把异常吞掉了，完全看不出来。
> 正确做法是让失败显式暴露出来（返回 500 或者明确的错误信息），而不是伪造一个看似合理的默认值。**这也是我对"防御性编程"理解的转折点——兜底要在正确的层次做，不能掩盖数据一致性问题。**

## 坑 16　Streamlit 每次 rerun 都重新上传 PDF

**现象**：聊两三句以后越来越慢。

## 坑 18　Windows 版 Redis 的 fork 问题

`Logs/redis_log.txt`（811 行）里反复刷：

**正确说法**：

**这个答案的价值在于：你知道哪些问题可以不管。** 这是工程判断力。

## 坑 19　emoji + Windows 控制台重定向 = 连锁故障

**实测复现**：
```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2705': illegal multibyte sequence
```

**根因**：Windows 控制台默认 GBK（cp936），而代码里用了 `✅`/`❌`。**输出重定向到文件或管道时更容易触发。**

**为什么这个坑特别值得讲**——它引发了连锁故障：

脚本死在 `print(f"[任务表行数] ...")` 这一行，导致后面 `r.delete(lkey)` **永远不执行**，那把锁**要等 300 秒 TTL 才自动过期**。

**一个 emoji，造成了一个 5 分钟的假故障。**

**修复**：统一 `sys.stdout.reconfigure(encoding="utf-8")`，或者把 emoji 换成纯文本标记。

**面试怎么讲**
> 我在测试脚本里用了 emoji 做标记，结果在 Windows 控制台重定向输出时抛了 `UnicodeEncodeError`。这个坑有意思的地方是它的**连锁反应**：脚本崩在打印那一行，导致后面释放 Redis 锁的代码永远没执行，那把锁要等 300 秒 TTL 才自动过期——**看起来像是 Redis 出了问题，其实是打印字符集的问题。**
> 这让我理解了 `finally` 块的价值：**资源释放不应该依赖前面所有代码都执行成功。**
