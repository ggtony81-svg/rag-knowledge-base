# 多智能体协作工坊 —— 白话讲解

> 和《RAG白话讲解》同一套讲法：不出现代码，不从名词开始，名词最后才出现。

---

# 一、一句话说清它在干什么

你输入一个需求（比如"用 Python 写一个批量重命名文件的脚本"），**四个 AI 角色轮流上，互相挑刺，改到满意为止**。

---

# 二、先破一个误解：「多智能体」其实只有一个 AI

这是最该先讲清楚的事。

看到"多智能体协作系统"，你可能以为里面住了四个不同的 AI，各有各的脑子。

**不是的。** 你项目从头到尾**只调用了同一个模型** —— DeepSeek。

那"四个角色"是什么？

**是四份不同的"人设说明书"。**

每次调用那个 AI 之前，先给它一张纸：

- 第一张：「你是一个**策划师**。分析需求，输出执行方案。」
- 第二张：「你是一个**执行者**。按方案干活，直接输出成果。」
- 第三张：「你是一个**严格的审查员**。找出问题，1-10 分打分。」
- 第四张：「你是一个**优化者**。按审查意见修改。」

**同一个 AI，换一张纸，就换一个人格。**

这就是"多智能体"的全部秘密。

---

# 三、那这样有用吗？为什么有用？

**有用，原理很朴素。**

问你自己：作业写完自己检查，容易发现问题吗？

**很不容易。** 你脑子里已经认定"我这么写是有道理的"，检查时会不自觉给自己找理由。

**但如果是同桌帮你检查呢？** 你会立刻认真起来，而且同桌没有你的思维定势，一眼就看出你漏了什么。

**"自己批评自己"难，"批评别人"容易。AI 也一样。**

- 直接问它："你刚写的这段代码怎么样？" → 它会说"挺好的，逻辑清晰"
- 换张纸说："**你是严格的审查员，找出至少 3 个具体问题，不许说空话**" → 它就开始真的挑了

**换一个身份，就换了一套评判标准。** 这就是这个项目能 work 的原因。

# 四、完整跑一遍

用"写一个批量重命名脚本"当例子。

**第 1 步 · 策划师**
拿到"你是策划师"那张纸，输出：

```
## 目标理解
用户要一个能批量给文件重命名的脚本
## 执行方案
1. 遍历目标目录
2. 支持自定义前后缀
3. 加预览模式先看效果
## 注意事项
...
```

**第 2 步 · 执行者**
拿到"你是执行者"那张纸，拿着策划师的方案，写出完整 Python 代码。

**第 3 步 · 审查员**
拿到"你是严格的审查员"那张纸，读代码，输出：

```
## 评分：7/10
## 仍然存在的问题
1. 没有处理文件名冲突
2. 缺少异常处理
3. ...
## 改进建议
...
```

**第 4 步 · 优化者**
拿到"你是优化者"那张纸，拿原代码 + 审查意见，改出新一版。

**然后回到第 2 步，再来一轮。**

第二轮里，执行者看到的不是"原始方案"，而是"上一版改过的成果" —— **接着改**。

审查员这次会拿到**两版对比**，被要求说清"相比上一版改进了什么"。

**最多 3 轮，或者审查员打到 8 分以上就提前收工。**

---

# 五、一个特别容易写错的地方：「上一版」

审查员的说明书里写着"对比上一版说明改进了什么"。

**但如果代码不把上一版塞给它呢？**

它会**瞎编** —— 说"相比上一版，这一版可读性有明显提升"，**但它压根没看到上一版**。

**AI 很擅长把不存在的东西说得头头是道。** 这是它的通病。

这里有个坑：

**第二轮开始时，"当前成果"会被新一轮的结果覆盖掉。**

所以必须在覆盖**之前**，先把它存进"上一版"变量。

**就像接力赛交棒** —— 你得先接住棒，才能交出去。顺序反了，棒就掉了。

（代码里就是循环开头那一行，把"当前成果"先存进"上一版"。）

---

# 六、什么时候停下来

两个条件：

1. 审查员打 **8 分以上** 且 **已跑满 2 轮** → 停
2. **跑满 3 轮** → 不管多少分也停

**为什么要求"跑满 2 轮"？**

第一轮就 8 分，可能只是审查员手松。**强制跑两轮**，逼它看过"上一版 vs 这一版"再决定。

---

# 七、一个很聪明的细节：读不懂分数时，默认给 7 分

审查员打完分，代码要从它的输出里**把数字抠出来**（找"评分：X/"这个模式）。

**但如果它不按格式写呢？** 比如写"评分：优秀"，那就抠不到数字了。

这时代码默认给 **7 分**。

**关键问题：为什么是 7，不是 10？**

因为：

- 及格线是 **8** 分
- **7 < 8 → 系统会继续再跑一轮**

**这是"宁可多跑一轮，也不要错误地停下来"。**

停错了 = 交给用户一个烂活；多跑一轮 = 多花点钱，但更保险。

**这个思路叫"兜底值" —— 读不到的时候，倒向安全的那个方向，不是倒向省事的那一边。**

（面试里这个细节很加分，说明你想过"出错了会怎样"。）

# 八、怎么跑到网页上的？（边跑边推）

AI 生成一次要几十秒。等它全跑完再给，你得对着空屏幕发呆一分钟。

所以**边跑边推**：

- 策划师做完 → 立刻推一条 → 网页冒出一张卡片
- 执行者做完 → 再推一条 → 又冒出一张卡片
- …

**像餐厅上菜**：做一道上一道，不是全部做完才一起端。你能看到进度，不至于以为死机了。

（这个技术的名字叫**流式输出**。你们 RAG 项目回答问题时也是这么干的。）

---

# 九、跑完的东西存哪？（MySQL）

存两张表：

**任务表** —— 记"有这么一个任务"（任务名、类型、需求、状态、时间）

**步骤表** —— 记"这个任务里的每一步"（哪一轮、哪个角色、说了什么、打分多少）

**为什么不合成一张表？**

一个任务有很多步。塞一张表里，"任务名"要重复写很多遍 —— **改一次任务名得改十几行。**

**分开：任务写一遍，步骤写多行。**

**还有个细节**：步骤表上挂着一条规则 —— "删任务时，它的所有步骤自动跟着删掉"。

**为什么需要？** 不然你删了任务，它的步骤还留在表里 —— **变成一堆找不到主人的孤儿数据**，越积越多。

# 十、Redis 在里面干什么（后加的部分）

## 用途一：防止手抖点两次

**问题**：一次协作要跑几十秒，而且每跑一次都花钱（要调用好几次 AI）。

用户在网页上等急了，手一抖又点了一次"启动" → **同一个任务跑了两份，钱花了两份。**

**解决**：开跑之前，先在 Redis 上"占个位子"。

> "这个需求现在有人跑了，5 分钟内别人不许再跑。"

**这里有个关键点：占位子必须是一步完成的动作。**

假设分成两步：先问"有人占了吗"，听到"没有"再去占。

**两个人同时问会怎样？** 两个人都听到"没有"，然后都去占 —— **都占上了，等于没锁住。**

**就像两个人同时看到同一个空车位，都问了一句"这有人吗"，都听到"没有"，然后都倒了进去。**

所以必须有个**一步到位的"看+占"**动作。Redis 正好提供了这个。

**还有个好处**：这个位子**自带 5 分钟倒计时**。万一程序崩了，位子自动释放，不会永久卡死。

## 用途二：缓存任务详情

**问题**：查看历史任务详情，要从 MySQL 拉一大堆 AI 生成的几千字长文本。**读得很慢，而且读的人多、改的人少。**

**解决**：第一次读完，把结果存 Redis。第二次读同样的任务，**直接从 Redis 给，不查库了。**

**效果**：131 毫秒 → 3 毫秒。

**还有个必须做的动作**：每次任务有新步骤保存时，要**把缓存删掉**。

**为什么删，而不是"更新"？**

更新很容易出岔子 —— 漏更新一个字段、更新顺序错了，就会出现"缓存里是旧数据、数据库里是新数据"，用户看到过期的。

**删掉最省心**：下次读的时候没有缓存，自然会去数据库重新拉一份最新的。

## 还有一个更重要的设计：Redis 挂了怎么办？

**答案：照样跑。**

- 抢不到锁 → 放行，不拦
- 缓存读不到 → 直接查数据库

**为什么这么设计？** 因为 Redis 在这个项目里是"锦上添花"，不是"命根子"。它挂了，系统慢一点、防不住重复提交，但**功能还是完整的**。

**就像安全气囊**：有它更安全，但它坏了，车照样能开。**不能因为气囊坏了就不让发动。**

# 十一、这个项目现在的一个短板

实测发现，审查员的分数经常**卡在 7 分**，导致几乎每次都跑满 3 轮。

可能的原因：

- 提取分数失败时会默认给 7 —— 如果审查员输出格式不稳定，就会一直是 7
- 审查员本身给分偏保守

**影响**：每次都跑满 3 轮 = 每次都花最多的钱和时间，而第 3 轮相比第 2 轮提升有限。

**为什么这个值得记住？** 面试官问"这个项目有什么可以改进的"，答这个，比答"还没做用户系统"专业得多 —— 因为它**基于真实观测**，而且指向具体的成本问题。

# 十二、面试怎么答

## 问：介绍一下这个多智能体项目？

> 用户输入需求，四个 AI 角色轮流处理 —— 策划、执行、审查、优化 —— 审查员打分，不满意就再改一轮，最多 3 轮。相当于给 AI 配了一组互相挑刺的同事。

## 问：你说的"多智能体"，是真有四个 AI 吗？

> 不是，其实是同一个模型，通过四份不同的提示词让它扮演四个角色。原理是：直接问 AI"你写得怎么样"，它会说挺好；但告诉它"你是一个严格的审查员，找出至少 3 个具体问题"，它就会真的开始挑。

## 问：那怎么判断什么时候停？

> 审查员会打 1-10 分，8 分以上就提前停，但强制至少跑 2 轮。因为第一轮就 8 分可能是审查员手松，强制跑两轮让它看过"上一版和这一版"再判断。最多 3 轮兜底。

## 问：有什么你觉得设计得比较有意思的地方？

> 有个兜底处理：代码要从审查员的输出里提取分数，但它没按格式写就提取不到。我设的默认值是 7 分 —— 因为及格线是 8 分，7 分会让系统继续再跑一轮。宁可多花一轮的钱，也不要错误地停下来交一个烂活。

## 问：Redis 在项目里做什么？

> 两个用途。一是分布式锁防重复提交 —— 一次任务要跑几十秒还烧钱，用户手抖点两次就会跑两份。用 SET NX EX 一步完成"检查+占位"，还自带过期时间，程序崩了也能自动释放。二是缓存任务详情，读多写少而且内容很大，缓存后从 131 毫秒降到 3 毫秒。

## 问：Redis 挂了会怎样？

> 不影响主流程。锁抢不到就放行，缓存读不到就查库。Redis 在这个项目里是加速和防呆，不是必需的。就像安全气囊，坏了车照样开。

## 问：这个项目有什么可以改进的？

> 实测发现审查员分数经常卡在 7 分，导致几乎每次都要跑满 3 轮。跑满 3 轮就是花最多的钱和时间，但第 3 轮相比第 2 轮提升有限。我怀疑是分数提取失败时的默认值造成的 —— 默认 7 分会让它一直迭代。这个还没修。

# 十三、名词对照

| 你会看到 | 其实就是 |
|---|---|
| 多智能体 / Multi-Agent | 同一个 AI 换几份人设说明书，轮流扮演不同角色 |
| Agent / 智能体 | 一个"有身份的 AI"，身份 = 你给它的说明书 |
| Prompt / 提示词 | 那张人设说明书 |
| System Prompt | 说明书里"你是谁、要干什么"那部分（和用户的具体问题分开写） |
| 工作流 / Workflow | 四个角色按什么顺序轮、什么时候停的那套规矩 |
| 轮次 / Round | 走一遍"执行→审查→优化"算一轮 |
| 迭代 / Iterate | 反复跑多轮，每轮比上轮好 |
| 流式输出 / Streaming | 边跑边推给前端，不是全跑完才给 |
| 分布式锁 | 在 Redis 上占个位子，防止同一件事被跑两遍 |
| 缓存 / Cache | 把读得多的结果存起来，下次直接给 |
| 缓存失效 | 数据变了就删缓存，下次读自然拿最新的 |
| 降级 | 附属功能坏了不影响主流程，凑合继续跑 |
| 兜底值 / 默认值 | 读不到的时候倒向安全那边的那个数 |
