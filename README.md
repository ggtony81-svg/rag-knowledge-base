# 项目一 · RAG 知识库问答系统（含离线评测体系）

上传 PDF 自动建库；提问时先检索出最相关的段落，再交给大模型**仅依据这些段落**作答，答案流式返回。

这个项目的重点不是"跑通了一个 RAG"，而是：**用一套离线评测体系，把检索方案的选择从"感觉"变成"数据"**。

---

## 一段话结论

通用向量模型 `bge-small-zh-v1.5` 在 CMRC2018 上的 P@1 只有 **85.9%**，**打不过关键词检索 BM25 的 91.6%**。

排查定位到两个原因：

1. **领域不匹配** —— 通用语料预训练的模型没见过本领域"问题 → 段落"的对应关系；
2. **静默截断** —— 语料平均 582 token，超出模型 512 的上限，**63.5% 的文档被截掉后半段，且不报任何错**。

分别修复后（结构分块 + 领域微调），P@1 达到 **92.4%**，与"向量 + CrossEncoder 重排序"方案的 P@1 **恰好相同**，
而单次检索从 **6345ms 降到 20ms 以内**，差了约两个数量级。

线上最终采用前者（分块 + 微调）。

## 评测驱动的检索选型

**评测集**：CMRC2018（哈工大讯飞中文机器阅读理解）—— 1149 条查询 / 934 篇语料，
每条查询有唯一的标准相关文档。指标按 BEIR 口径计算。

| 方案 | P@1 | Recall@3 | Recall@10 | MRR@10 | nDCG@10 | 单次耗时 |
|---|---|---|---|---|---|---|
| A · BM25 关键词 | 0.9164 | 0.9721 | 0.9878 | 0.9455 | 0.9561 | 7.1 ms |
| B · 向量检索 | 0.8590 | 0.9017 | 0.9460 | 0.8863 | 0.9007 | 18.1 ms |
| C · 向量 + 重排序 | **0.9243** | 0.9399 | 0.9460 | 0.9327 | 0.9360 | 6345.7 ms |
| D · 向量检索（微调） | 0.8895 | 0.9356 | 0.9669 | 0.9158 | 0.9283 | 21.9 ms |
| E · 分块 + 向量检索 | 0.9051 | 0.9434 | 0.9634 | 0.9262 | 0.9353 | 19.0 ms |
| **F · 分块 + 微调** | **0.9243** | **0.9600** | **0.9861** | **0.9445** | **0.9545** | **15.5 ms** |

三个值得说的点：

- **B < A 是反直觉的**。语义检索通常被认为强于关键词检索，但在这里输给 BM25 近 6 个百分点。
  如果只看 B 就下"向量检索更好/更差"的结论，方向就错了——问题出在数据没有适配模型，而不是模型不好。
- **E、D 分别验证了两个原因**。分块单独带来 +4.6pt（B→E），微调单独带来 +3.0pt（B→D），
  两者叠加后是 +6.5pt（B→F）。注意 4.6 + 3.0 = 7.6，比实际的 6.5 大 ——
  叠加增益小于各自单独增益之和，说明这两条改进**有部分重叠**：分块把完整段落交到模型手里之后，
  微调学到的东西才能全部用上，单独做微调时还有一半文本被截在外面。
  但两个方向各自都是正收益，所以都要做。
- **F 和 C 的 P@1 恰好相同（都是 0.9243），但两者的起点不一样**。C 是在**基础模型**之上做的重排序，
  F 是**分块 + 微调**。C 的召回上限被基础模型卡死了（Recall@10 只有 0.9460），F 是 0.9861。
  换句话说，"在 F 之上再加重排序"这件事**并没有测过**，不能据此说重排序没用。
  数据能支持的说法是：**在当前这个评测集上，重排序相对 F 没有额外收益，代价却高两个数量级**，
  因此线上不采用。这个结论和评测集绑定，换到领域差异大的语料上不一定成立——那时重排序仍是备选。

> 关于耗时：只有耗时是浮动的。同一份代码、同一个数据集，E 两次跑出 16.7 ms 和 19.0 ms，
> F 跑出 17.4 ms 和 15.5 ms，机器负载不同就有 ±15% 的波动，所以耗时只适合看数量级。
> 指标不受算力影响：重跑一遍 E/F，全部指标与首次运行**浮点数完全相等**。

> 完整数据：`eval/results/retrieval_summary.md`
> 逐次运行的原始结果：`eval/results/retrieval_*.json`

### 端到端评测（200 条）

检索对了，大模型就一定能答对吗？单独测了一次。

判"答对"的口径是**标准答案是否出现在回答中（包含率）**，不是 EM —— 原因见下一小节。

| | |
|---|---|
| 检索命中标准段落 | 197 / 200（**98.5%**） |
| &nbsp;&nbsp;└ 其中答对 | **88.3%** |
| 检索未命中 | 3 / 200（1.5%） |
| &nbsp;&nbsp;└ 其中答对 | **0.0%** |

**检索没命中时答对率是 0**，说明这个系统的瓶颈在检索，不在生成。
不过也要看到：200 条里已经有 197 条检索是对的，生成端再优化也只能动剩下那 3 条。

#### 一个坑：EM 会严重低估生成式回答

同一批 200 题、同一套检索、同一个模型、同一天跑的，只把提示词从
"基于资料回答问题"换成"只给出答案本身"，指标就变成：

| 提示词风格 | EM | F1 | 包含率 | 检索命中率 |
|---|---|---|---|---|
| system（线上实际使用） | 0.045 | 0.471 | **0.870** | 0.985 |
| concise（对照实验） | **0.765** | **0.924** | 0.855 | 0.985 |

检索命中率完全相同（检索本身跟提示词无关），包含率也只差 1.5 个点，
但 **EM 差了 17 倍**。

原因是 EM 要求回答与标准答案**逐字相同**，而线上提示词本来就要求模型
"基于资料回答问题"，模型会把答案写进完整句子里 —— 标准答案是"十个工作日"，
回答是"出差结束后十个工作日内提交出差报告并完成报销"，意思完全正确，
字面却对不上。

所以这个项目用**包含率和 F1** 作为主要口径，EM 只作参考。
（图见 `eval/results/figures/fig7_提示词风格对照.png`）

### 避免指标虚高

微调前检查了训练集与评测集的重叠：CMRC2018 训练集里有 **204 篇文档同时出现在评测语料中**，
剔除后才开始训练。不剔的话模型相当于做过这些题，指标会好看但不可信。

## 两个工程决策

### 1. 为什么线上没有用重排序

CrossEncoder 重排序确实有用（C 比 B 高 6.5pt），而且在方案 F 上**可能还有用——只是没测**。
之所以最后没上，是因为在已经跑过的方案里，F 的 P@1 和 C 相同（都是 0.9243），
而检索耗时是 **15ms 量级 vs 6345ms**，差两个数量级。为了一个当前已经拿到的指标付出这个延迟，不划算。

需要说清楚的是，这是一个**基于已有实验的取舍**，不是"重排序无效"的结论。
要严格证明它在 F 之上也没有增益，得再跑一个方案 G（分块 + 微调 + 重排序）——
本项目的实验到此为止，没有做。如果将来语料换成领域差异大的场景、F 掉下来了，
重排序仍是第一个值得重新试的选项，代码在 `eval/retrievers.py` 里保留着。

### 2. 知识库落盘要带"指纹"

向量库序列化到磁盘时，会一并记录**生成它的模型路径、分块参数、向量维度**。
启动加载时逐项比对，不一致就拒绝加载并提示重新上传。

原因：换了 embedding 模型却沿用旧向量，相似度**照样算得出来**（维度都是 512），
只是算出来的是错的 —— 不报错、不崩溃，静默给出错误排序。
这类"错误伪装成成功"的问题比崩溃难查得多。

## 架构

```
上传阶段
  PDF ──PyMuPDF──▶ 纯文本 ──smart_chunk_v2──▶ 文本块 ──微调模型──▶ 向量 ──▶ 落盘
                            (400 token 上限               (bge-small-zh
                             / 50 token 重叠)              + 领域微调)

问答阶段
  问题 ──▶ Redis 缓存 ──命中──▶ 直接返回（不调模型）
              │未命中
              ▼
         向量化 ──▶ 与全部块做矩阵乘 ──▶ Top-3 ──▶ 拼进 Prompt ──▶ DeepSeek 流式生成
                                                                      │
                                              写回 Redis 缓存 ◀───────┘
                                              写入 MySQL 会话历史
```

**MySQL 和 Redis 不可用时全部走降级分支**（缓存直查、锁放行），主流程不受影响。
这一点是实测过的：把 Redis 停掉再问，检索和回答都照常（见 `eval/run_blackbox_tests.py` 的 T12）。
`/status` 会如实返回 `cache_on: false`，而不是报错——状态接口本来就是用来看服务好没好使的，
它自己先挂了就失去意义了。

# 项目二 · 多智能体协作系统 · AI 协作工坊

4 个 AI 角色（**策划师 → 执行者 → 审查员 → 优化者**）轮流处理同一份产物：
上一轮的产出作为下一轮的输入，最多迭代 3 轮。每一步的结果实时流式推到浏览器，
任务和每步产出落库，支持历史回放与删除。

```
需求
 │
 ▼
策划师 ── 制定方案
 │
 ▼
执行者 ── 产出成果  ◀────────────────┐
 │                                   │
 ▼                                   │
审查员 ── 打分（1-10）+ 列出具体问题    │
 │                                   │
 ├─ 分数 ≥ 8 且已跑满 2 轮 ──▶ 结束    │
 │                                   │
 ▼                                   │
优化者 ── 按审查意见修改 ──────────────┘
```

强制至少跑满 2 轮：第 1 轮就打出高分的审查结果未必可信，多跑一轮再看。

## 三个工程点

### 1. 打分提取失败时，默认值故意选在阈值之下

审查员返回的是自然语言，分数需要从文本里正则提取：

```python
m = re.search(r'评分[:：]\s*(\d+)\s*/', critic)
final_score = int(m.group(1)) if m else 7
```

提取失败时默认 **7 分**，而继续迭代的阈值是 **8 分** —— 默认值**落在阈值以下**，
系统于是选择"再跑一轮"，而不是"判定完成"。

方向是刻意选的：**提取失败说明审查结果没能被正确解析，这种情况下结束流程的风险更大**。
宁可多烧一轮 token，也不要因为解析失败就把没改好的产物当成成品交出去。

> 已知的粗糙点：实测审查员输出 `8.5/10`、`8分/10`、`8 （满分10分）` 这三种常见写法，
> 当前正则都会提取失败、落到默认值。代价是多跑一轮，不是出错 —— 由"保守默认值"兜住了。

### 2. Redis 分布式锁防止重复提交

一次协作要跑十几秒、连调十几轮大模型，用户手滑点两次就会跑两份、烧两份 token。

```python
r.set(key, "1", nx=True, ex=300)   # SET NX EX：原子写入 + 自带过期时间
```

用 `SET NX EX` 而不是"先查再写"，因为**查和写之间有间隙** —— 两个并发请求可能同时查到"锁不存在"，
然后都认为自己拿到了锁。`EX` 让锁自带过期时间：进程崩了锁也会自动释放，
不会像数据库行锁那样被永久占住。

锁在 `finally` 里释放 —— 正常跑完、中途断流、抛异常，三种情况都要放锁。

### 3. Redis 全链路可降级

锁、缓存、读、写，每一处 Redis 调用都包了 `try/except`：

| 情况 | 行为 |
|---|---|
| 拿锁时 Redis 不可用 | **放行**，不阻塞主流程 |
| 读缓存失败 | 回落到直接查 MySQL |
| 写缓存失败 | 忽略，MySQL 才是数据源 |

**设计取舍**：Redis 在这里是加速器，不是数据源。它挂了只应该损失速度和防重能力，
不应该让用户连任务都提交不了。

## 快速开始

```bash
python agent_studio_api.py     # 后端启动在 http://127.0.0.1:18007
```

然后直接用浏览器打开 `studio.html`（前端是独立页面，通过 CORS 调用后端）。

## 技术栈

| 环节 | 技术 |
|---|---|
| 后端 | Python · FastAPI · StreamingResponse 流式输出 |
| 大模型 | DeepSeek API（OpenAI 兼容格式）· 4 个角色用 system prompt 区分 |
| 锁与缓存 | Redis（`SET NX EX` 分布式锁 · Cache-Aside，含全链路降级） |

| 前端 | 原生 HTML + CSS + JS，无框架 |

任务详情接入 Cache-Aside 缓存后，读接口从 **131ms 降到 3ms**。
