**项目**：基于检索增强的 PDF 知识库问答系统
**检查日期**：2026-10-02
**检查范围**：本仓库全部代码、评测产物、README 文档

---

## 一、为什么要做这次质检

写论文之前必须先确认一件事：**论文里要引用的每一个数字，背后都有一条能重跑的产物链**。

本科大作业最容易出问题的地方不是代码写错，而是写完代码之后顺手在文档里写了一句"性能提升了三倍"，结果这个"三倍"既没有实验数据支撑，也没人再去核对。论文一旦引用了这种数字，后面就全是麻烦。

所以这次质检的判定标准只有一条：**凡是写进 README、准备搬进论文的数字，都必须能追溯到 `eval/results/` 下的某个文件，并且能重新算出来。**

检查分三类问题：

| 类别 | 含义 | 处理要求 |
|---|---|---|
| **A 类** | 会导致论文失实的表述或数据 | 必须改，改完重新核对 |
| **B 类** | 代码真实功能缺陷 | 必须修，修完重新测试 |
| **C 类** | 一致性、整洁性问题 | 顺手处理 |

---

## 二、检查方法

检查没有靠"通读一遍觉得没问题"，而是用了四种能被验证的手段：

1. **写脚本反查文档数字** —— 把 README 里出现的每个数值提取出来，与 `eval/results/` 里的 JSON 逐一比对，而不是眼睛看。
2. **重跑实验做复现性验证** —— 方案 E、F 重新跑了一遍，比对指标是否与首次运行一致。
3. **对关键数字做独立复算** —— 例如"训练集与评测语料重叠 204 篇"，不看代码注释里写的数，而是自己重新求交集算一遍。
4. **对线上服务做黑盒测试** —— 服务真实跑起来，用 12 个测试用例打真实 HTTP 接口，而不是只读代码判断"应该没问题"。**并且在 Redis 开、停两种状态下各跑一轮**——只测"依赖都正常"是不够的，B4 这个 bug 就是这么漏掉的。

B1 是三个里最值得说的一个。它不崩溃、不报错，界面上一切正常，只是答案来自错误的文档。这类"错误伪装成成功"的问题，比直接 500 难发现得多。

### 4.2 方案 E/F 重跑：指标浮点完全相同

`eval/results/repro_check.log` 记录了 2026-10-02 的重跑结果。与 2026-09-26 首次运行对比：

| 方案 | P@1（09-26） | P@1（10-02） | 结论 |
|---|---|---|---|
| E 分块向量检索 | 0.9051348999129678 | 0.9051348999129678 | 完全相同 |
| F 分块+微调 | 0.9242819843342036 | 0.9242819843342036 | 完全相同 |

这一点我没有藏起来，而是在 README 里明确写了"耗时只适合看数量级"。理由很简单：CPU 上跑，机器负载不同结果就不同，把它写成精确值反而是在制造一个经不起追问的数字。指标不受影响，因为指标是确定性的计算结果。

README 和代码注释都写"评测语料 934 篇中有 204 篇与训练集重叠"。不看注释，自己重新求交集：

- T07 最初判为不通过，我核对知识库后发现是**判定器错了**——"病假超过三十天的需经人力资源部审批"确实写在手册第十五条。已改用数字溯源判定，这条如实记录在此。

### 4.5 截断问题有了可复现的量化证据

`eval/analyze_truncation.py` 逐篇过 tokenizer 统计，输出 `chunking_analysis.json`：

| 处理方式 | 块数 | 每篇块数 | 平均长度 | 最大长度 | 被截断比例 |
|---|---|---|---|---|---|
| 整篇直接编码 | 934 | 1.00 | 582.1 | 975 | **63.49%** |
| `smart_chunk`（只按章节切） | 934 | 1.00 | 582.1 | 975 | **63.49%** |
| `smart_chunk_v2`（结构+句边界切） | 1973 | 2.11 | 303.1 | 399 | **0.0%** |

这张表解释了"通用向量模型为什么打不过 BM25"：63.5% 的文档后半段被模型**静默丢弃**，不报错、不警告，检索照样返回结果，只是拿不到后半篇。

**这里有一处必须说清楚**：`smart_chunk` 和"整篇直接编码"两行的数字**完全相同**，不是巧合——`smart_chunk` 在这个语料上**一篇文档都没切开**（`pct_doc_unchunked: 100.0`）。因为它只认"第X章""第X条"这类结构标记，而 CMRC2018 的语料是维基百科式的段落，**根本没有章节编号**。所以它退化成了"整篇编码"，截断率自然一模一样。

这不是 bug，而是第五节 5.4 提到的 `_SECTION_PREFIXES` 局限在这个数据集上的直接体现。也正因为如此，方案 E 用的是 `smart_chunk_v2`（在结构切分之上补充了按句边界的长度切分），而不是 `smart_chunk`——只按结构切在这里等于没切。

这张表也说明了 v2 的代价：块数从 934 涨到 1973（约 2.1 倍），每篇文档的块变多但每块更短。检索时要在更多块里找，但换来的是**没有任何一块被截断**。

### 4.6 提示词风格对照实验

质检过程中补的一个实验，结论与 README 原有表述相反，因此整节重写。

同一批 200 题、同一套检索、同一个模型、同一天、随机种子都是 42，**只改提示词**：

| 提示词风格 | EM | F1 | 包含率 | 检索命中率 |
|---|---|---|---|---|
| system（线上实际） | 0.045 | 0.471 | **0.870** | 0.985 |
| concise（对照） | **0.765** | **0.924** | 0.855 | 0.985 |

**EM 差了 17 倍**，但检索命中率完全相同（检索本身跟提示词无关）。原因是 EM 要求逐字相同，而线上提示词要求"基于资料回答问题"，模型会把答案写进完整句子里。

这个实验有两个作用：一是说明本项目为什么用包含率和 F1 而不是 EM；二是确认了"瓶颈在检索"这个结论**不依赖于 EM**——因为它用的是包含率口径。

正则匹配不到评分时**兜底给 7 分**。这会让"审查员打分"看起来永远有效，实际是默认值。这是另一个项目的问题，不影响本项目的结论，但**论文写多智能体部分时不能拿它当证据**。

### 5.4 分块实现有一处已知局限

`text_chunk.py` 里的结构标记表 `_SECTION_PREFIXES` 是**写死的短表**，只覆盖"第一章~第三章""第一条~第七条"。超出范围的章节号不会被识别为结构边界，会退回按句子切分。

这个局限在代码注释里已如实写明。**如果后续改动了这张表，本文中所有与分块相关的结论都不再适用**。

### 写论文时必须遵守的三条底线

1. **不引用第五节 5.2 列出的任何文件**作为项目成果证据；
2. **不声称做过方案 G**（分块+微调+重排序），这是没做过的实验；

### 一个诚实的说明

这次质检改的不是"错误"，而是**说话的分寸**。数据一直是干净的，问题出在从数据到结论的那一步多走了。
